# ADR-001: Разделение ролей Architect и Executor

- **Статус:** Принято
- **Дата:** 2026-09-24
- **Источник:** Анализ Aider Architect Mode

## Контекст

При последовательном выполнении бэклога использование единой флагманской модели (Opus/o3) для всех этапов приводит к неприемлемой стоимости. Анализ Aider показал, что разделение planning и editing на две модели снижает стоимость в 5-20x без потери качества.

Проблема: сильные reasoning-модели плохо генерируют точные file edits. Слабые модели плохо планируют. Попытка использовать одну модель для обоих этапов — компромисс, проигрывающий по обоим параметрам.

## Решение

Ввести строгое разделение ролей:

1. **Planner** (was "Architect"): Сильная модель (Claude Opus, o3). Получает бэклог и контекст проекта. Строит/корректирует граф задач. НЕ редактирует файлы напрямую.
2. **Executor**: Дешёвая модель (Qwen-Coder, Haiku, Sonnet). Получает узкую задачу из графа + релевантный контекст. Генерирует правки в diff-fenced формате.
3. **Reviewer** (опционально): Может быть детерминированным (lint/test) или LLM (для сложных проверок). Проверяет результат Executor.

Переключение моделей происходит автоматически на уровне оркестратора. Пользователь может override через конфигурацию задачи.

## Последствия

- ✅ Снижение стоимости выполнения бэклога в 5-20x
- ✅ Улучшение качества планирования (сильная модель фокусируется на структуре)
- ✅ Улучшение качества правок (слабая модель оптимизирована под code generation)
- ⚠️ Увеличение latency (два LLM-запроса вместо одного)
- ⚠️ Необходимость чёткого контракта между Planner и Executor (формат плана)
- ⚠️ Риск потери нюансов при передаче от Planner к Executor

## Альтернативы

1. **Единая модель** — отклонена: неприемлемая стоимость, компромиссное качество
2. **Fine-tuned single model** — отклонена: высокая стоимость поддержки, не гибко
3. **Dynamic model selection per task** — рассматривается для P1, но MVP требует простоты
