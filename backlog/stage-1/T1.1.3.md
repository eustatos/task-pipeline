# Implement role-based tool access in the registry

## Objective
Enforce role-based access at the registry level by adding
`get(tool_name, role)` and `list_for_role(role)`. A role may only access tools
whose `ToolSpec.roles` includes that role.

### Not Included
- Graph-level routing by role (Stage 2)
- Authentication of the role identity
- Concrete tool implementations (Stage 3)

## Context
DoD criterion C0.3 requires zero cross-role tool leaks between Architect,
Executor and Reviewer. Access must be denied centrally in the registry, not
scattered across the orchestration layer (ADR-006).

## Tech Stack & Constraints
- Python 3.11 (`ToolRegistry` from T1.1.2, `AgentRole` from T1.1.1)

## Input/Output Contracts

```python
class ToolRegistry:
    def get(self, name: str, role: AgentRole) -> ToolSpec: ...
    def list_for_role(self, role: AgentRole) -> list[ToolSpec]: ...
```

- `get` raises `AccessDeniedError` when `role` is not in `spec.roles`
- `list_for_role` returns only tools that include `role`

## Acceptance Criteria

| ID | Input | Expected Behavior | Verification |
|----|-------|-------------------|--------------|
| AC1 | Architect requests a planning tool | Tool returned | `pytest -k architect_allowed` |
| AC2 | Executor requests a planning-only tool | `AccessDeniedError` raised | `pytest -k cross_role_denied` |
| AC3 | `list_for_role(Executor)` | Only Executor tools returned | `pytest -k list_for_role` |
| AC4 | Role absent from all specs | Empty list returned, no error | `pytest -k empty_role` |

## Boundaries

| Tier | Rules |
|------|-------|
| Always | Deny by default when a role is absent; filter in the registry layer |
| Ask First | Adding new roles to `AgentRole`; changing denial semantics |
| Never | Leak a tool across roles; perform role checks in callers instead of the registry |
